# คู่มือการสร้างใบสั่งซื้ออัตโนมัติจากการเติมสต็อก (Auto PO from Replenishment)

## 1. วัตถุประสงค์

เอกสารนี้อธิบายการใช้งานหน้าจอ `Replenishment` ใน Odoo สำหรับสร้างการเติมสต็อกที่นำไปสู่การสร้าง `RFQ / Purchase Order` อัตโนมัติเมื่อ `Route = Buy` โดยอธิบาย:

- ทุก field และปุ่มที่เห็นบนหน้าจอ
- กดตรงไหนแล้วไปหน้าจอไหนต่อ
- กดแล้วระบบคำนวณหรือสร้างข้อมูลอะไร
- จุดที่เป็นมาตรฐาน Odoo และจุดที่ฐานนี้มี custom เพิ่ม

ขอบเขตของคู่มือนี้อ้างอิงหน้าจอ `Inventory > Operations > Replenishment` ตามรูปที่ใช้งานในระบบ `view`

## 2. ภาพรวมการทำงาน

หน้าจอ `Replenishment` ใช้สำหรับบอกระบบว่า ถ้าสต็อกสินค้าต่ำกว่าที่ต้องการ ระบบควรเติมสต็อกอย่างไร เช่น:

- ซื้อเข้า (`Buy`)
- ผลิต (`Manufacture`)
- ดึงจากคลังอื่น (`Auto Transfer`)
- สั่งตามออเดอร์ (`Replenish on Order / MTO`)

ถ้าตั้ง `Route = Buy` และมีข้อมูลผู้ขายพร้อม ระบบจะสร้างหรืออัปเดต `RFQ / Purchase Order` ให้เมื่อสั่ง Replenish

สรุป flow ของ `Auto PO from Replenishment`

1. ผู้ใช้เปิดหน้าจอ `Replenishment`
2. ผู้ใช้สร้างหรือแก้รายการเติมสต็อก
3. ผู้ใช้กำหนด `Product`, `Location`, `Route = Buy`, `Trigger`, และปริมาณ
4. ผู้ใช้กด `Save`
5. ผู้ใช้กด `Order` หรือ `Automate`
6. ระบบสร้าง procurement
7. Procurement rule ฝั่งซื้อทำการสร้างหรืออัปเดต `RFQ / PO`
8. ผู้ใช้ไปตรวจสอบเอกสารต่อที่ `Purchase`

### 4.3 ตารางรายการ Replenishment

| คอลัมน์/ปุ่ม | ความหมาย | กรอกได้หรือไม่ | รายละเอียดการทำงาน |
| --- | --- | --- | --- |
| Checkbox หน้าแถว | ใช้เลือกหลายรายการพร้อมกัน | ได้ | ใช้ร่วมกับ action แบบกลุ่ม เช่น Replenish หรือ Snooze หลายรายการ |
| `Product` | สินค้าที่ต้องการตั้งกติกาเติมสต็อก | ได้ตอนสร้าง/แก้ไข | เลือกสินค้าที่จะให้ระบบติดตามการเติมสต็อก |
| `Location` | คลัง/ตำแหน่งเก็บที่ต้องการให้มีของ | ได้ตอนสร้าง/แก้ไข | เป็นปลายทางที่ระบบใช้คำนวณ On Hand, Forecast และสร้าง procurement |
| `On Hand` | ยอดคงเหลือที่มีอยู่จริงใน location | ไม่ได้ | ระบบคำนวณอัตโนมัติจาก stock on hand ปัจจุบัน |
| `Forecast` | ยอดคาดการณ์หลังรวม incoming/outgoing | ไม่ได้ | ระบบคำนวณจากสต็อกปัจจุบัน บวกของเข้า ลบของออก และรายการที่กำลังดำเนินการ |
| ไอคอนกราฟข้าง Forecast | เปิด forecast report | ได้ | ระบบเปิดหน้ารายงาน forecast ของสินค้านั้นเพื่อดู incoming/outgoing เชิงลึก |
| `Route` | วิธีเติมสต็อก | ได้ | ระบุว่าระบบควรซื้อ ผลิต ดึงจากคลังอื่น หรือใช้ route อื่นเมื่อเกิดความต้องการเติมสต็อก |
| ไอคอน `i` ข้าง Route | Replenishment Info | ได้ | ระบบเปิดหน้าข้อมูลประกอบการเติมสต็อก เช่น lead time และรายละเอียด supplier/in-progress บางกรณี |
| `Trigger` | วิธีการกระตุ้นการเติมสต็อก | ได้ | `Manual` ให้ผู้ใช้สั่งเอง, `Auto` ให้ระบบมองเป็น reordering rule อัตโนมัติ |
| `Min` | ค่าขั้นต่ำที่ต้องการให้มี | ได้ | ถ้า Forecast ต่ำกว่า Min ระบบจะคำนวณว่าจะสั่งเติม |
| `Max` | ค่าสูงสุดหรือเป้าหมายหลังเติม | ได้ | ระบบใช้เป็น target หลักในการคำนวณ `To Order` เมื่อ Forecast ต่ำกว่าเกณฑ์ |
| `To Order` | ปริมาณที่ต้องสั่งเติม | ได้เฉพาะ manual หรือบางจังหวะที่ระบบเปิดให้แก้ | ถ้าเป็น manual ผู้ใช้กรอกเองได้ ถ้าเป็น auto ระบบคำนวณให้และ field จะอ่านอย่างเดียว |
| Undo icon ข้าง `To Order` | ลบ manual qty | ได้เมื่อมี manual qty | ระบบล้างค่าที่ผู้ใช้ override ไว้และให้กลับไปใช้ค่าคำนวณอัตโนมัติ |
| `UoM` | หน่วยนับของสินค้า | ไม่ได้ | ดึงจากสินค้าโดยอัตโนมัติ |
| `Order` | สั่งเติมสต็อกทันที | ได้เมื่อ `To Order > 0` | ระบบสร้าง procurement ทันที ถ้า `Route = Buy` จะไปสร้างหรืออัปเดต RFQ/PO |
| `Automate` | เปลี่ยนรายการ manual ให้เป็น auto แล้วสั่งเติมทันที | ได้เมื่อแถวเป็น manual และ `To Order > 0` | ระบบเปลี่ยน `Trigger = Auto` แล้วเรียกการสั่ง Replenish ต่อทันที |
| `Snooze` | พักรายการชั่วคราว | ได้เฉพาะ manual | ระบบเปิด wizard ให้เลือกวันที่พัก รายการจะถูกซ่อนจากมุมมอง `Not Snoozed` จนถึงวันที่กำหนด |

### 4.4 รายละเอียดของค่าใน `Route`

ค่าที่เห็นใน dropdown ขึ้นอยู่กับ route ที่เปิดใช้ในระบบ ตัวอย่างจากหน้าจอ:

| Route | ใช้เมื่อไร | ผลที่ระบบทำ |
| --- | --- | --- |
| `Buy` | ต้องการให้เติมสต็อกโดยการซื้อจาก vendor | ระบบสร้าง procurement ฝั่งซื้อ และนำไปสร้าง/อัปเดต `RFQ / PO` |
| `Manufacture` | ต้องการให้เติมสต็อกโดยการผลิต | ระบบสร้าง procurement ฝั่งผลิต และไปสร้าง `MO` |
| `Replenish on Order (MTO)` | ต้องการให้เติมตาม demand จริง | ระบบสร้าง supply ตาม demand ที่เกิดขึ้น |
| `Auto Transfer MTS / RM / Semi` | ต้องการโยกของจากคลังต้นทางที่กำหนด | ระบบสร้าง internal transfer ตาม route นั้น |
| `Resupply Subcontractor on Order` | ใช้กับ subcontracting | ระบบสร้าง flow สนับสนุนงาน subcontract |

### 4.5 รายละเอียดของค่าใน `Trigger`

| Trigger | ความหมาย | พฤติกรรมของระบบ |
| --- | --- | --- |
| `Manual` | ผู้ใช้เป็นคนตัดสินใจว่าจะสั่งเมื่อไร | ผู้ใช้กรอก `To Order` เองได้, ใช้ `Order`, `Automate`, `Snooze` ได้ |
| `Auto` | ใช้เป็น reordering rule อัตโนมัติ | ระบบคำนวณ `To Order` จาก `Min/Max/Forecast`, field `To Order` จะไม่เปิดให้ override แบบ manual ตาม flow ปกติ |

## 5. ตาราง “กดตรงนี้แล้วเกิดอะไรขึ้น”

| ผู้ใช้กดตรงไหน | ไปไหนต่อ | ระบบทำอะไรเบื้องหลัง |
| --- | --- | --- |
| `New` | อยู่หน้าเดิม | เพิ่มแถวใหม่ด้านล่างสุดเพื่อสร้าง orderpoint |
| เลือก `Product` | อยู่หน้าเดิม | โหลดข้อมูลสินค้า, UoM, และใช้ข้อมูลนี้ไปคำนวณ forecast/replenishment |
| เลือก `Location` | อยู่หน้าเดิม | เปลี่ยน context ของ stock ที่ใช้คำนวณ On Hand และ Forecast |
| เลือก `Route = Buy` | อยู่หน้าเดิม | กำหนดว่าถ้าสั่งเติม ระบบจะใช้ procurement rule ฝั่งซื้อ |
| กดไอคอนกราฟที่ Forecast | Forecast report | เปิดรายงาน forecast ของสินค้านี้ |
| กดไอคอน `i` | Replenishment info | เปิดข้อมูลเพิ่มเติมเรื่อง lead time / supplier / replenishment context |
| เปลี่ยน `Trigger = Manual` | อยู่หน้าเดิม | เปิดโหมดให้ผู้ใช้กำหนด `To Order` เองและใช้ `Snooze` ได้ |
| เปลี่ยน `Trigger = Auto` | อยู่หน้าเดิม | ให้ระบบมองรายการนี้เป็น reordering rule อัตโนมัติ |
| กรอก `Min` / `Max` | อยู่หน้าเดิม | ระบบใช้เป็นเกณฑ์คำนวณจำนวนที่จะสั่งเติม |
| กรอก `To Order` | อยู่หน้าเดิม | ถ้าเป็น manual ระบบเก็บค่า override เพื่อใช้ตอนกด Order |
| `Save` | อยู่หน้าเดิม | บันทึก rule ลงฐานข้อมูล แต่ยังไม่สร้าง PO จนกว่าจะสั่ง Replenish |
| `Order` | อยู่หน้าเดิมและอาจมี notification | เรียก `action_replenish` สร้าง procurement ทันที ถ้า route เป็น Buy จะสร้างหรืออัปเดต RFQ/PO |
| `Automate` | อยู่หน้าเดิมและอาจมี notification | เปลี่ยน trigger เป็น Auto แล้วเรียก Replenish ต่อทันที |
| `Snooze` | เปิด Snooze wizard | บันทึกวันที่พักรายการ ทำให้รายการไม่ขึ้นในมุมมอง `Not Snoozed` ชั่วคราว |

## 6. อธิบาย field ที่ต้องกรอกเพื่อให้เกิด Auto PO

### 6.1 Field ที่จำเป็น

| Field | ต้องใส่หรือไม่ | คำอธิบาย |
| --- | --- | --- |
| `Product` | ต้องใส่ | ต้องเป็นสินค้าที่ต้องการเติมสต็อก |
| `Location` | ต้องใส่ | ต้องระบุ location ปลายทางที่ต้องการให้มีของ |
| `Route` | ต้องใส่ | ถ้าต้องการให้ระบบออก PO ต้องเลือก `Buy` |
| `Trigger` | ควรใส่ | เลือก `Manual` ถ้าต้องการ review ก่อนสั่ง หรือ `Auto` ถ้าต้องการเป็น rule อัตโนมัติ |
| `Min` / `Max` | ควรใส่ถ้าจะใช้ auto rule | ระบบใช้คำนวณว่าจะสั่งเท่าไร |
| `To Order` | ต้องมีค่ามากกว่า 0 ตอนจะกดสั่ง | ถ้าเป็น manual อาจกรอกเอง ถ้าเป็น auto ระบบจะคำนวณให้ |

### 6.2 เงื่อนไขที่ต้องพร้อมเพื่อให้ `Route = Buy` สร้าง PO ได้จริง

| เงื่อนไข | ถ้าไม่พร้อมจะเกิดอะไร |
| --- | --- |
| สินค้ามี vendor / supplier info | Procurement ฝั่งซื้ออาจสร้าง PO ไม่ได้ หรือขึ้น procurement exception |
| Route ของสินค้าหรือ orderpoint รองรับ `Buy` | ระบบจะไม่ไปฝั่งซื้อ |
| `To Order > 0` | ปุ่ม `Order`/`Automate` จะไม่ทำให้เกิดการซื้อ |
| สิทธิ์ผู้ใช้เข้าถึง Purchase/Inventory ตาม flow | ผู้ใช้บางคนอาจสั่งเติมได้แต่เปิดดู PO ไม่ได้ |

## 7. ขั้นตอนทำงานแบบทีละคลิก

## 7.1 แบบที่ 1: สร้างรายการแล้วกด `Order` เพื่อออก PO ทันที

เหมาะกับกรณีที่ผู้ใช้ต้องการควบคุมจำนวนสั่งด้วยตนเองก่อน

1. เข้าเมนู `Inventory > Operations > Replenishment`
2. ตรวจว่าหน้าอยู่ในมุมมอง `Replenishment`
3. คลิก `New`
4. ที่แถวใหม่ด้านล่าง กรอก `Product`
5. เลือก `Location`
6. เลือก `Route = Buy`
7. เลือก `Trigger = Manual`
8. กรอก `To Order` ให้มากกว่า `0`
9. ถ้าต้องการเก็บเป็นกติกาไว้ด้วย ให้กรอก `Min` และ `Max`
10. คลิก `Save`
11. ตรวจว่าปุ่ม `Order` แสดงที่แถวรายการ
12. คลิก `Order`

ผลที่เกิดขึ้น

- ระบบเรียกกระบวนการ `Replenish`
- ระบบสร้าง procurement ของสินค้านี้ตามจำนวน `To Order`
- เนื่องจาก `Route = Buy` ระบบจะพยายามสร้างหรืออัปเดต `RFQ / Purchase Order`
- ถ้ามี draft PO เดิมที่เงื่อนไข grouping ตรงกัน ระบบอาจเพิ่ม line เข้า PO เดิม แทนการสร้าง PO ใหม่
- ถ้าระบบสร้างเอกสารซื้อได้ อาจมี notification ให้เปิดเอกสาร PO/RFQ ที่สร้าง

ไปดูผลลัพธ์ต่อที่:

`Purchase > Requests for Quotation`

หรือ

`Purchase > Orders`

## 7.2 แบบที่ 2: สร้างรายการแล้วกด `Automate`

เหมาะกับกรณีที่ต้องการให้รายการนี้กลายเป็น auto rule และสั่งเติมทันทีในครั้งนี้ด้วย

1. เข้าเมนู `Inventory > Operations > Replenishment`
2. คลิก `New`
3. เลือก `Product`
4. เลือก `Location`
5. เลือก `Route = Buy`
6. เลือก `Trigger = Manual` หรือใช้ค่าเริ่มต้นที่เป็น manual
7. กำหนด `Min`, `Max`, และ/หรือ `To Order`
8. คลิก `Save`
9. คลิก `Automate`

ผลที่เกิดขึ้น

- ระบบเปลี่ยน `Trigger` ของแถวนี้เป็น `Auto`
- จากนั้นระบบเรียก `Replenish` ต่อทันที
- ถ้า `Route = Buy` ระบบจะสร้างหรืออัปเดต `RFQ / PO`
- หลังจากนั้นรายการนี้จะทำงานในฐานะ reordering rule แบบ auto สำหรับรอบถัดไป

## 7.3 แบบที่ 3: ตั้งเป็น `Auto` rule แล้วค่อยให้ระบบรันตามรอบ

เหมาะกับกรณีต้องการเก็บกติกาไว้ให้ scheduler หรือผู้ใช้มาสั่งในภายหลัง

1. คลิก `New`
2. เลือก `Product`
3. เลือก `Location`
4. เลือก `Route = Buy`
5. เปลี่ยน `Trigger = Auto`
6. กรอก `Min` และ `Max`
7. คลิก `Save`

ผลที่เกิดขึ้น

- ระบบบันทึก reordering rule แบบ auto
- ยังไม่จำเป็นต้องเกิด PO ทันทีจากการกด `Save` อย่างเดียว
- เมื่อมี demand/forecast ต่ำกว่ากติกา ผู้ใช้สามารถกด `Order` จากหน้าจอ หรือให้ระบบรันการเติมสต็อกตามรอบงานที่กำหนด

## 8. ลำดับการไหลของข้อมูลหลังจากกด `Order` หรือ `Automate`

### 8.1 เมื่อ `Route = Buy`

1. ผู้ใช้กด `Order` หรือ `Automate`
2. ระบบสร้าง procurement จากรายการ Replenishment
3. Procurement rule ฝั่งซื้อทำงาน
4. ระบบค้นหา vendor/supplier info ของสินค้า
5. ระบบสร้างหรืออัปเดต `RFQ / PO`
6. ผู้ใช้ไปตรวจสอบเอกสารที่ `Purchase`

### 8.2 เมื่อ `Route` ไม่ใช่ `Buy`

ถ้าเลือก route อื่น ระบบจะไม่สร้าง PO แต่จะไปตาม route นั้น เช่น:

- `Manufacture` -> สร้าง `MO`
- `Auto Transfer` -> สร้าง `Internal Transfer`
- `MTO` -> สร้าง supply ตาม demand ของ route นั้น

## 9. พฤติกรรมมาตรฐาน Odoo กับ custom ในฐานนี้

### 9.1 มาตรฐาน Odoo

พฤติกรรมมาตรฐานที่คู่มือนี้อ้างอิง:

- หน้า `Replenishment` ใช้ model `stock.warehouse.orderpoint`
- `Manual` เปิดให้กรอก `To Order` เองได้
- `Auto` ใช้ `Min/Max/Forecast` คำนวณจำนวนสั่ง
- `Order` เรียกการสั่งเติมทันที
- `Automate` เปลี่ยนเป็น auto และสั่งเติมทันที
- `Snooze` ใช้พักรายการ manual ชั่วคราว

### 9.2 Custom ที่พบในฐานนี้

ใน code ของระบบนี้มี custom เพิ่มเติมกับ flow `Auto PO from Replenishment` โดยเฉพาะเมื่อเกิดเอกสารซื้อจาก Replenishment:

- ถ้า PO ที่เกิดมีลักษณะมาจาก `Replenishment` / `MTO` / `OP`
  ระบบอาจส่ง notification หรือ activity เพิ่มเติม
- ในบางกรณีระบบอาจแจ้งเตือน `Auto PO Replenishment (Plastic/Pharma)`
- บาง flow อาจมีการ assign buyer/ผู้รับผิดชอบตามประเภทการผลิต

สรุปคือ หลังจากกด `Order` หรือ `Automate` ในฐานนี้ อาจไม่ได้มีแค่การสร้าง PO แต่ยังอาจมี `alert` หรือ `activity` ตาม custom เพิ่มเข้ามา

## 10. จุดสังเกตสำคัญสำหรับผู้ใช้

| ประเด็น | คำอธิบาย |
| --- | --- |
| กด `Save` อย่างเดียว ยังไม่สร้าง PO | `Save` แค่บันทึก rule หรือรายการเติมสต็อก |
| กด `Order` หรือ `Automate` จึงเริ่ม procurement | สองปุ่มนี้คือจุดที่ทำให้ระบบเริ่มสร้าง supply document |
| `Route = Buy` เท่านั้นที่ไปสร้าง PO | ถ้าเลือก route อื่น ระบบจะไปสร้างเอกสารชนิดอื่น |
| `To Order` ต้องมากกว่า 0 | ถ้าจำนวนเป็น 0 จะไม่มีอะไรให้ระบบสั่ง |
| `Snooze` ใช้ได้เฉพาะ manual | auto trigger ไม่ใช่รายการที่ intended ให้พักด้วยวิธีนี้ |
| Auto ไม่ได้แปลว่ากด Save แล้วมี PO ทันทีทุกกรณี | Auto คือกติกาอัตโนมัติของ orderpoint ส่วนการสร้างเอกสารขึ้นกับการเรียก replenish/scheduler และ demand จริง |
